## 环 12 · 收敛与呈现形态：先把十三份文件收成唯一真源，再决定看板长什么样

**思维**：进入交付阶段前，我不接受在一堆迭代过的文件上直接填数和做看板——那会把被取代的版本和陈旧数字一起嵌进去。所以先梳理：每个文件读出最终态，标出被取代项和跨文件冲突，合并成一张指标总表；填数和看板都从这张表出发。呈现形态上，我原本想的是 TradingView 式指标看板；看到经济日历页面后，我追问的不是「好不好看」，而是「来得及吗、在这个题目情景下有必要吗」。

**你的指令（原话）**："每个大的文件内部可能有拼接…需要去领会…最终希望的该板块一个最终的状态是什么样"；"前端这种事件式我觉得也很创意 来得及做吗 或你觉得在这个题目情景下有必要吗"。

**纠偏（改前 → 改后）**

| 项 | 改前 | 改后 |
|---|---|---|
| 工作底稿 | 十三份迭代文件并存，陈旧项散落（early_A、signal_stream、三版 valuable_score、RBRK 旧数、尾仓名单缺口） | 一份总梳理稿 + 一张指标总表为唯一真源；11 处陈旧项显式修正；原文件不动作 L0 证据 |
| 呈现形态 | K 线式指标看板 | 经济日历式：时间轴 = knowledge_time；Actual / Forecast / Prior = 实测 / 预期基准 / 上期；重要性只显 H/M/L |
| 未来行 | 无 | 排期行标日期依据（公司公告 / 规则推定 / 估计 / 待定），把题面的「更新频率」变成可见排期 |

**这一环体现的特质**：不在脏底稿上叠加工作（planning 先行、不推倒重来）；对形态追问「必要吗」（critical）；K 线让位给日历，是形态服从体系纪律（思路优先）。

## 环 13 · 真数核验：查证 agent 拉源，我方二次抽核，措辞跟着原文走

**你的指令**：（本环按 E27 授权执行，无新指令；但沿用你在环 2 的原则："用真实的数据，不要示例值…来源做详细分类…持续管理"）

**纠偏（改前 → 改后）**

| NBIS ARR / 承诺 / 预付 / 5 GW / 单价 | P2 电话会转述 | P1 股东信原文 | SHLQ226.pdf 本地抽核 |

## 环 14 · 看板构建：三次被数据打回的设计

**思维**：看板不是画出来就完，我让 AI 每改一版就在浏览器里跑、截图、看控制台。三处问题都是数据反过来纠正设计：

**纠偏（改前 → 改后）**

| 项 | 改前 | 改后 | 为什么 |
|---|---|---|---|
| Actual 列 | 整段长文本入表，撑坏布局 | 表内只显首段短值，全文进抽屉 | 表是扫描面，抽屉是阅读面 |
| 三态点 | 「本期实测 vs 全年指引」被判成「不及」 | 除人工裁量的对账节点外一律灰 | 不同期不能比；不编假信号 |
| hyperscaler capex | 四家挤在一行，Alphabet 的日历行显示 MSFT 值 | 拆四行原子事实 + 一行合计（计算值 P5，假设 C11） | doc21 §〇「字段存原子事实」在呈现层再次被验证 |

**边分数补齐**：RBRK / FCEL / 尾仓 14 条边按 doc21 §六 算出可交易度 / 预警度，因子赋值逐条登记（假设 A9）。读出一个值得审的点：尾仓 NVDA 代理边可交易度高于光模块→NBIS，但独家性低——可交易度 ≠ 独家价值，两者要分开看。

**这一环体现的特质**：呈现层的每个设计决定都能回溯到体系原则（原子事实、不同期不比、只排序不定量）；先跑再交，不交没跑过的东西。

## 环 15 · 图要不要：先问「谁在什么场景下需要什么」，再问「画不画」

**思维**：看板 v2 的抽屉里已经把每个节点的边列成了文字，我看到旧的蝴蝶结图时没有直接说「加回来」，而是先问 AI：以信息论和基金数据负责人的视角，这张图有没有必要、原因是什么。它答必要后我再逼一层：这套体系面向谁、什么场景、什么意图、图旁边还要同屏什么、和现有主视图的区别在哪，按「用户 → 场景 → 意图 → 信息 → 形式」拆。不拆清楚就加视图，只会让看板变成两张好看的图。

**你的指令（原话）**："这种节点图我觉得有必要呈现 形式可以讨论…你是信息论专家和对冲基金ai数据资深负责人 你觉得是否有必要 原因是什么"；"这个体系面向谁 服务哪种情景下的何种需求 用户用到图的时候还会需要哪些信息需要在同一个视图呈现 和现有主视图区别在哪 现有主视图也是这个原理 根据用户-场景-意图-需要的信息-最优呈现形式 这样来分析"。

**纠偏（改前 → 改后）**

| 项 | 改前 | 改后 |
|---|---|---|
| 图的定位 | 「旧图贴回来」 | 同一张 registry 的第二种投影：日历按 knowledge_time 答 when，图按 edge_registry 答 so what；研究员工作流里是一次点击的前后两步 |
| 图上同屏什么 | 不明确 | 必须：节点最新值 + P 级、下次数据点日期、边跳数 / tier / 两分数、票权重与 regime、中间机制节点；不要：来源全文、假设台账、验证方法（留抽屉） |
| 图怎么来 | 手画 SVG | 从边总表数据驱动，加 `chain` 列存中间节点；图、抽屉、日历三处永远一致 |
| 用户落点 | 一个看板 | 研究员在日历，PM 在图，数据岗在树和 CSV，评审者在每行的 P 级和 owner |

**这一环体现的特质**：对「要不要加一个视图」也走 planning 先行，先定用户和场景再定形式；追问不止于「必要」，还要「和现有的区别在哪」，防止功能叠加而无增量。

## 环 16 · 定位纠偏：入口是研究员的，出口却是数据岗的

**思维**：看板 v3 做完我自己走了一遍研究员的路径：在日历里看到 xAI 融资这条，想知道它对持仓的影响，点开却是 schema、来源、备注；只有最底下一个小按钮跳映射图，跳过去也不是这条信息的子图。同时数据岗看那段多事实的 hero 文本也没法维护。我没有说「把抽屉改好看」，而是追问：这个看板到底为谁、什么场景、怎么实现、问题在哪；再追问数据岗要不要看板，还是数据库就够，以及底层数据现在怎么管、工具栈是什么。

**你的指令（原话）**："从分析需求出发 有种场景：我会在页面1看到某条感兴趣的信息 想了解它对持仓的影响…现在点这条 右侧主要显示的是指标schema、来源、备注等for数据人员的信息 对研究用处有限…映射图并非和我点击跳转的那条信息有关…for数据人员 图4这种形式的可维护性、直观性又有限"；"数据岗需要看板吗 还是用数据库就行 如果需要 为什么…我们现在底层的数据是怎么管理的 工具栈如何"；"1啥意思"；"拆"。

**AI 认账的根因**：填数时为了快，把多条观测塞进 registry 的 value_latest 一格，违反了 doc21 §〇「字段存原子事实」和 R / fct 分表的设计。抽屉之所以只能是记录卡，是因为数据只有一格。这和 capex 四家挤一行是同一个错误，环 14 只改了一处。

**纠偏（改前 → 改后）**

| 项 | 改前 | 改后 |
|---|---|---|
| 数据层 | 值是 registry 里一段话 | `13-观测记录.csv` 173 条，一行一个事实；registry 退回纯定义；表内值构建时推导，不落库 |
| 研究面出口 | schema 抽屉 | 影响卡：这是什么 → 打到谁 → 多确定 → 接下来盯什么；证据表；数据卡折叠 |
| 图的上下文 | 高亮一个节点 | 聚焦模式：只显示受影响的票，无关边淡出，面包屑可清除 |
| 表的列 | 三态列常年灰 | 换成「打到谁」列：受影响票 + 权重 + 占优类型 |
| 数据岗 | 想再做一套界面 | 不做：集合型问题用视图和告警；看板只留过期标记与状态计数 |
| 边表覆盖 | 23 条 | 影响卡暴露 5 个节点无边 → 补 6 条，29 条 |

**这一环体现的特质**：从用户路径倒推产品定位，而不是从功能清单正推；对「数据岗要不要看板」这种看似理所当然的问题也问一遍「为什么」；发现根因在数据层就先拆表，不在界面上打补丁。

## 环 17 · 常驻区的两道筛：每次都看吗，看一眼够吗

**思维**：我拿 TradingView 的 screener 对照我们的右栏和顶栏，先让 AI 说设计逻辑合不合理。它给了一版更全的 watchlist 和三个下拉、四个预设，我没接，追了一句：从信息密度和使用频率看合理吗，右栏和顶栏是常驻信息，要简洁、要高频。这句话是标准，不是意见。

**你的指令（原话）**："你参考图三 tradingview screener sidebar 的设计逻辑 思考下图12现在的设计逻辑合理吗 用户什么情景会需要 需要啥样的"；"从信息密度和使用频率 你觉得合理吗 因为右栏和顶栏是常驻信息 需要简洁且高频使用需求"。

**纠偏（改前 → 改后）**

| 右栏每行 | 票、权重、维、P 徽章、一段异构 KPI 文本 | 五格数字 | 票、权重灰字、一个注意力信号（↑7 天新数据 · 下次几天） |

**这一环体现的特质**：对 AI 的「更完整」方案说不，用一句可执行的标准（常驻 = 简洁 + 高频）替代逐项讨论；标准一给，方案自己收敛。

## 环 18 · 关键事实是写出来的，不是拼出来的；下钻是一页，不是一个抽屉

**思维**：我要右栏下方有一段像 TradingView Key facts 那样的总结，省得点回链接；事件名变成链接进下钻。AI 第一次把「关键事实」理解成字段模板拼接、把下钻理解成抽屉里嵌图。我纠正：关键事实是这条信息的前因后果、关键数据、相关方，是有人写的简报；下钻要像 TradingView 的 symbol 页那样整个主区切换，并让它先把下钻页的内容设计出来。

**你的指令（原话）**："把这条的key fact总结 省的我点回链接查看…事件名做个跳链 点击事件名再显示下钻详情"；"关键事实不是这个信息/事件的前因后果关键数据相关方这些吗 不是字段的重复；下钻做整个主区切换…我们下钻页的内容放哪些也思考设计下"。

**纠偏（改前 → 改后）**

| 项 | AI 第一版 | 修正后 |
|---|---|---|
| 关键事实 | 从记录值和备注模板拼 | 57 条手写简报（前因 / 数据 / 相关方 / 后果 + 盯什么），只用已有记录，B 级初稿待复核 |

**这一环体现的特质**：区分「信息」和「字段」，字段可以推导，信息必须有人负责；对形态的要求落到具体参照物（TradingView symbol 页）并要求先设计再做。

## 环 19 · 面板为谁，就用谁的问题定列；分类不是形式，是推导链的入口

**思维**：AI 把 TradingView 的 watchlist 逻辑照搬成「对象分组 × 四列」，列里有「下一个数据点几天」。我问的是：这些列研究员真的要吗。研究员和 PM 用 AI 发展数据，是要常规数据给不了的东西，和 TradingView 并不严格对应，要回到基金场景想。下钻页也一样：不是按量价、事件、前沿分 Tab 就叫分类，而是不同类型的数据推导到选股决策的逻辑不同，推导节点不同，所需信息不同，呈现才不同，要 by case 梳理。AI 列出七类后我再问一句会不会太多，收敛成三个模板加票页。

**你的指令（原话）**："我们这个面板的定位不是数据管理人员，而是研究员和PM…你的行和列这些信号是不是都有用…要结合我们对冲基金数据的这个场景去做深入的思考"；"不同类型的数据，它带来的信息含义，包括它到我们最后去做选股的决策的逻辑都是不同的…推导节点不同…对应所需要的信息也不同…要by case去分析"；"1做 2这7类会不会太多了"。

**纠偏（改前 → 改后）**

| 项 | AI 第一版 | 修正后 |
|---|---|---|
| 信号表的列 | 权重 · ↑7d 新观测数 · 下次几天 · 信号 | 五个决策时刻反推：链状态（供需政）· 本周动了什么 · 预警 · 领先读；验证点降为灰字且只保留能证伪 thesis 的 |
| 列的依据 | 有什么数据就显示什么 | 每列对应一个决策时刻：持有期、财报前、风险、证伪、轮动 |
| 下钻分类 | 按数据类分 Tab | 按推导角色分模板：领先 / 本体 → 序列与对账；事件 / regime → 事件与机制；前沿 / 观点 → 表述与证伪；角色作为一列标在主板上 |
| 模板数 | 七 | 三 + 票页，四个 Tab 共用 |
| 新字段 | 无 | 观测记录加方向判断（A11，B 初稿 D 复核，不进阈值） |

**这一环体现的特质**：把「为谁」落到「他在什么时刻问什么」，再倒推列；把分类从界面问题还原成推导链问题；对方案数量也问一句「会不会太多」，控制复杂度。

## 环 20 · 词表给谁用，增量在哪一级，缩略层长什么样

**思维**：面板做出来我一看，字段全是我们讨论时的词：供需政、regime、链状态、验证点、盯、预警、书。TradingView 能只写「Beta 0.36」是因为那是外部标准；我们这些是自己分析过程里的构造，有价值，但直接摆给使用者就是理解成本。所以先问：这些词到底 for 谁。再问：从 PM 和研究员看，改后的面板够不够专业，以及我们「AI 发展 base」的增量到底体现在哪，不能空说，我们的上游节点、前沿观测、信号分层都是为这个服务的。AI 给的上游读数表我一看，光模块、capex、融资，这是常规投研，不 AI。最后一层：右下角是缩略层，每类内容用最直观的形式，图能说清就用图，细节留给整页。

**你的指令（原话）**："用户不知道你呈现的某个值…到底是啥意思…这个是肯定不行的"；"怎么体现我们是AI发展base的…不要空穴来风，其实我们之前是做了很多这样的事情的"；"没懂，这里看起来好像不是很AI呀"；"右下角那个面板，它是一个缩略的…最直观的形式可以用图"。

**纠偏（改前 → 改后）**

| 项 | 改前 | 改后 |
|---|---|---|
