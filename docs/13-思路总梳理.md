## 二 九个板块最终态

### B1 口径与两轴（doc 16）
**一句话**：「AI 发展」= 能力前沿义 + 产业变现义合流；实体只存两条不可推导的轴。
- 纵轴 = 价值栈 L1 硬件 → L2 云 / 平台 → L3 模型 → L4 数据 / 工具 → L5 应用 → L6 终端 / 具身（在哪变现）。
- 横轴 = 成熟度 research / private / pre_ipo / public（信号多早）。
- 早期信号层 = maturity ∈ {research, private} 的**视图**；三子流（研究前沿 / 创业一级 / 人才资本）= 视图内按 data_class 派生，**不是字段**（E24）。
- 五个前沿向量横切：scaling 是否起效 / 推理时计算与端侧 / 新范式 / 开源 vs 闭源 / 数据飞轮与护城河。
- 中国侧是每层的附加标签，不是主判据（E19）。
- 排除项：AI-washing、无因果的主题炒作、无可观测信号的纯早期项目（进雷达不进核心）。
**状态**：最终态保留；三子流叙述须按视图读（见第四节 #3）。

### B2 数据类型与字段（doc 17）
**一句话**：数据的结构决定一切，四类各自派生 schema / 载体 / 频率 / 分工 / 呈现。
- 类 1 量价（规则时序，可回归）· 类 2 事件（离散关系，可建图）· 类 3 观点（带发言人的分级文本，codebook）· 类 4 前沿（海量知识流，聚类）。
- 通用元数据层四组：溯源（record_id / source_id / anchor / snapshot_id / knowledge_time / ingest_time）· 口径（unit / currency / frequency / version）· 质量（owner / confidence / code_score / judge_score / status）· 关联（entity_id / ticker_map / layer / maturity / data_class / signal_role / valuable_score）。缺一不进资产库。
- 载体栈：raw 快照 → 资产层（Postgres，按 knowledge_time 索引）→ 处理 trace（Langfuse）→ 呈现。
- Wave 路径：0 骨架 → 1 核心成熟层 → 2 同赛道向早期推 → 3 相邻赛道 → 4 全市场 + 雷达；每 wave 只加行不改 schema。
**状态**：最终态保留；valuable_score 定义以 doc 21 §六 为准（见第四节 #4）。

### B3 schema 双真源（doc 21 终版 + doc 22）
**一句话**：字段存不可再推导的原子事实，可推导的分组一律作视图；R + E 双真源。
- entity_master（layer × maturity 两轴）· entity_ticker_map（relation + map_path + weight）· v_early_signal 视图。
- metric_registry = R：每指标一行元数据（dim D1–D7 / data_class / signal_role / source_ids / frequency / lead_time_est / owner / valuable_score / status）。
- edge_registry = E：from_metric → to_ticker，side / edge_type E1–E6 / hops / cert_tier T1–T3 / cert_method / tradable_score / warning_score / evidence_ids。
- 四类 fct 表 + 四补丁：① conversion_assumption ② amount_type + is_estimate ③ map_path ④ lead_time_est。fct_frontier 另加 source_stance / verifiability / industry_impact / impact_rationale（doc29）。
- §六 打分：因子锚 H/M/L = .9/.6/.3；节点 valuable = 0.45e + 0.25s + 0.20r + 0.10φ；边 tradable = c·r·s·φ，warning = τ·l·e；weight 归一。**全部系数是假设，只用于排序**（doc30 A1–A8）。
- 视图 A（v_signal_latest，按 D1–D7）/ 视图 B（v_ticker_map，按 ticker）。
**状态**：doc 21 为终版；doc 22 的实体 INSERT 有陈旧写法（第四节 #1）。

**一句话**：从票向上游沿六类边数跳数；V = f(传导, 节点质量) 落成可交易度 / 预警度两产出；每条边过三层验证。

## 八 看板形态决策（E28）

**决策**：TradingView 经济日历式；静态单文件 HTML；数据内嵌；无后端；不做 K 线。

**为什么它比 K 线看板更贴这套体系**
1. knowledge_time / point-in-time 是体系的核心纪律，日历就是时间轴的用户界面，每行天然带「何时可知」。
2. 四类数据里三类是离散发布或事件；Actual / Forecast / Prior 恰好对应 实测 / 预期基准（signal_role = expectation_base）/ 上期，偏离即三态。
3. 题面要「更新频率」；未来行把频率变成可见排期（三季报截止、13F 申报日、海关月报、财报日），比表里写「季 / 月 / 事件」有说服力，也贴研究员的真实工作流。

**元素映射**

| TradingView | 本体系 |
|---|---|
| 日期分组 | knowledge_time（过去）/ next_release（未来，标依据类型） |
| 国旗 | entity.country：CN 凸显中国侧 |
| 重要性条 | is_key / valuable：只显 H/M/L，不显数字（doc30 只排序） |
| Actual | value_latest |
| Forecast | expectation_base：只放公司指引 / 公开一致预期 |
| Prior | prior_or_yoy |
| 分类 Tab | 全部 / 持仓 / D1–D7 / 前沿雷达 / regime |
| 右栏 watchlist | 视图 B 持仓票 ↔ 视图 A 七维树 切换 |
| 符号详情 | 行抽屉：源链接 / P 级 / owner / 假设 ID 与状态 / 关联边 tier / map_path |

**映射图视图（E33 补）**：主区「日历 / 映射图」切换。图 = 同一张 registry 按 edge_registry 的投影，答「打到谁」；每票一个蝴蝶结，从 `13-边总表.csv` 数据驱动（`chain` 列存中间机制节点）；节点同屏最新值 + P 级 + 下次数据点，边同屏跳数 / tier / 两分数；与日历、抽屉双向联动。用户落点：研究员在日历，PM 在图，数据岗在树与 CSV，评审者在每行 P 级与 owner。

**取舍与风险**：不做图表库；类 1 指标 ≥ 3 点才给 SVG sparkline。未来日期三种依据必须显式：公司公告 / 规则推定 / 估计（另有待定）。付费与合规项在日历里以 🔵 / ⚪ 出现但无值，诚实可见。

## 十 思维链 环 12 草稿（供 doc 31 续写）

**环 12 · 收敛与呈现形态：先把十三份文件收成唯一真源，再决定看板长什么样**

思维：进入交付阶段前，我不接受在一堆迭代过的文件上直接填数和做看板——那会把被取代的版本和陈旧数字一起嵌进去。所以先梳理：每个文件读出最终态，标出被取代项和跨文件冲突，合并成一张指标总表；填数和看板都从这张表出发。呈现形态上，我原本想的是 TradingView 式指标看板，看到经济日历页面后追问：事件式来得及吗、在这个题目情景下有必要吗。

你的指令（原话）："每个大的文件内部可能有拼接…需要去领会…最终希望的该板块一个最终的状态是什么样"；"前端这种事件式我觉得也很创意 来得及做吗 或你觉得在这个题目情景下有必要吗"。

纠偏（改前 → 改后）：

| 项 | 改前 | 改后 |
|---|---|---|
| 工作底稿 | 十三份迭代文件并存，陈旧项散落 | 一份总梳理稿 + 一张指标总表为唯一真源；11 处陈旧项显式修正 |
| 呈现形态 | K 线式指标看板 | 经济日历式：时间轴 = knowledge_time；Actual / Forecast / Prior = 实测 / 预期基准 / 上期；重要性只显 H/M/L |
| 未来行 | 无 | 排期行标日期依据（公司公告 / 规则推定 / 估计），把「更新频率」变成可见排期 |

这一环体现的特质：不在脏底稿上叠加工作（planning 先行、不推倒重来）；对呈现形态也追问「必要吗」而不是「好看吗」（critical）；把 K 线让位给日历，是因为形态要服从体系的纪律（思路优先）。
